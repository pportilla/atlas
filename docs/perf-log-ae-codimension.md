# Performance log: `ae_codimension`

This log records the performance work on the extended left-right
codimension (`ae_codimension`, `atlas algebra ae-codimension`). Each entry
names the hot spot and explains why the change applies to arbitrary inputs.
It also gives timings before and after, and says how the results were
compared.

* Baseline: commit `bd68f89` ("Create and name polynomial rings with ring()
  in Atlas sessions"), built with `make -j8`. A copy of its `native/build`
  directory served as the reference build for every comparison.
* Changes:
  1. `4f051e8`: incremental Hilbert numerator.
  2. `d322667`: graded surface ranks.
  3. `e7ae909`: jet rows.
* Machine: 13th Gen Intel Core i7-1355U (2 performance cores with 2 threads
  each, 8 efficiency cores), Manjaro Linux 6.18, FLINT 3.6.0, GMP 6.3,
  OpenBLAS 0.3.34.
* Load: other Atlas sessions were running throughout. The load average stayed
  between 8 and 18 during the timed runs. The before-and-after tables of
  entries 1–3 were pinned to logical CPU 2, a performance core. The baseline
  sweep, the profiles and the last two columns of the rank-loop table in
  entry 2 were not pinned.
* Timing method: the builds were alternated, with one discarded warm-up per
  build. The tables give the median and, where useful, the range.
* Kernel times come from `benchmarks/ae_codimension_kernel.cpp` in
  `solve-once` mode: one call in a fresh process, parsing and startup
  excluded. CLI times are the wall time of a fresh
  `native/build/local_algebra ./atlas algebra ae-codimension ...` process.

## Workload

The target workload is the map germ $(x^a, y^b, (x+y)^c)$ from the plane to
3-space, with $a, b, c$ pairwise coprime:

```sh
./atlas algebra ae-codimension --vars x,y --compute cpu --json \
  --component 'x^5' --component 'y^7' --component '(x+y)^9'
```

The prompt, scripts, HTTP and the CLI all reach the same native function
`atlas::local::ae_codimension` (`native/ae_codimension.cpp`). It runs a few
jet degrees, then calls `ae_graded` (`native/ae_graded.cpp`). For these maps
`ae_graded` first tries the graded rank method for surface maps
(`native/ae_graded_surface.cpp`). If that method declines, it computes a
lexicographic Gröbner basis of the 8-variable graph ideal
(`packed_lex_heads` in `native/local_basis.cpp`).

### Baseline sweep

All 60 pairwise-coprime triples $2\le a<b<c$ with the smallest $a+b+c$ were
run once each with a 60 s timeout:

* 19 finished with `graded_tangent_ranks` in 0.4–17 ms of kernel time. The
  largest last weight was 155, for (3,7,8).
* The other 41 timed out, among them (4,5,9), (5,6,7), (3,7,10), (5,7,9)
  and (3,5,13).
* A separate CLI run of (5,7,9) was stopped after 29 minutes without an
  answer.

The rank method had a fixed cap of weight 160. Past it the solver fell back
to the graph Gröbner basis. On its own, that basis is far more expensive.
The table was measured with `benchmarks/ae_graph_basis_kernel.cpp` on the
baseline build, unpinned:

| --- | ---: | ---: | ---: | ---: |
| (2,3,5) | 183 elements, 4,664 terms | 169 bits | 0.13 s | 0.13 s |
| (2,3,7) | 269 elements, 11,552 terms | 480 bits | 0.49 s | 0.59 s |

## 1. Incremental Hilbert numerator (`native/hilbert.cpp`, commit `4f051e8`)

**Hot spot.** `perf record --call-graph dwarf` of the Hilbert-driven route on
the graph ideal of (3,4,5), children view:

```
90.02%  atlas::hilbert_basis -> Engine::compute_homogeneous
66.62%  Engine::reduce_terms<false>
40.16%  atlas::merge
24.56%  atlas::remove_reduction_content
22.24%  Engine::leading_numerator -> atlas::hilbert_numerator
22.31%  (anonymous namespace)::numerator        (16.77% self)
```

`compute_homogeneous` compares the Hilbert function of the leading monomials
found so far with that of the ideal, at every new degree. Each time it
recomputed the numerator of the whole monomial ideal from scratch.

**Change.** Each new leading monomial $h$ now updates the numerator through
the exact sequence $0\to S/(M:h)(-\deg h)\to S/M\to S/(M+(h))\to 0$, that
is $N(M+(h)) = N(M) - t^{\deg h} N(M:h)$. The colon ideal is generated by
the $g/\gcd(g,h)$. The final certificate still recomputes the numerator of
the reduced basis from scratch.

**Why it is generic.** This is the Hilbert-driven Buchberger route of the
shared engine. `Engine::compute` uses it for every lexicographic or
elimination order that swells, whatever the caller. The update is an
identity of polynomials, so every value of `missing` is the same and the
algorithm makes the same choices.

**Timings.** The graph ideals (`Engine::compute`, the call `packed_lex_heads`
makes), 3 runs each:

| Graph ideal of | Before | After | Basis fingerprint |
| --- | ---: | ---: | --- |
| (2,3,5) | 0.188 s | 0.098 s | identical |
| (2,3,7) | 0.963 s | 0.478 s | identical |
| (3,4,5) | 9.08 s | 6.77 s | identical |

Maps of infinite codimension still end in graph elimination. Below, "after"
is the build with this change only (fresh CLI and kernel, 3 runs). Here
ae_graded_surface is unchanged and declines at weight 160 as before:

| Map | CLI before | CLI after | Kernel before | Kernel after |
| --- | ---: | ---: | ---: | ---: |
| $(x^2,y^3,x^5+y^5)$ | 17.5 ms | 16.6 ms | 2.35 ms | 2.11 ms |
| $(x^3,y^4,x^5+y^5)$ | 22.5 ms | 23.2 ms | 8.61 ms | 8.88 ms |

**Verification.**
* The harness prints a fingerprint of every leading monomial, and another
  of every term and coefficient of the reduced basis. Both were identical
  before and after on (2,3,5), (2,3,7) and (3,4,5).

  the six AE test modules, the 12 benchmark maps and the 60 coprime triples.
  179 complete records were byte-identical, apart from the elapsed-time
  fields. The 41 triples that timed out took 30 s or more on both builds.

## 2. Graded surface ranks (`native/ae_graded_surface.cpp`, commit `d322667`)

**Hot spot.** A perf profile of the running baseline (5,7,9) CLI
process, children view:

```
94.31%  ae_codimension -> ae_graded -> packed_lex_heads -> compute_packed_basis
        -> Engine::compute -> hilbert_basis -> compute_homogeneous
        -> reduce_terms -> remove_reduction_content
67.53%  fmpz_gcd
50.62%  __gmpn_addmul_1_x86_64   (self)
```

The graded rank method stopped at weight 160, a fixed cap, and declined.
Graph elimination then spent its time on coefficients of thousands of bits.
With the cap lifted, the rank method proves (5,7,9) at weight 299.

Lifting the cap alone made infinite inputs much slower. On
$(x^5,y^7,x^9+y^9)$ the rank loop ran 6.2 s before declining, and on
$(x^7,y^9,x^{10}+y^{10})$ more than 5 minutes. The profile showed exact rank
on rank-deficient pieces:

```
52.99%  _nmod_vec_dot2                  (fmpz_mat_rank)
 7.85%  nmod_mat_lu_classical_delayed
 6.96%  _nmod_vec_nored_ll_scalar_addmul
```

**Change.**
* *Modular ranks first.* A piece of full rank modulo a prime has full rank
  over $\mathbb Q$, so the zero pieces of the certificate are proved by
  modular ranks alone. The loop now finds the tail with modular ranks only.
* *Exact ranks afterwards.* Once a tail is proved, the loop computes exact
  ranks for the pieces the prime left unproved, in weight order. It stops
  at the first tail proved over $\mathbb Q$, so `value` and `last_weight`
  are those of the previous all-exact loop. A map of infinite codimension
  never reaches the exact ranks here.
* *Bounds.* The fixed cap of 160 is gone. The search ends at the existing
  degree bound $abc+\max(a,b)$ or at the existing per-matrix memory bound
  (600,000 entries). Both only select an algorithm.
* *Second prime.* If no tail is proved by then, the unproved pieces are
  ranked again modulo 65519 before the method declines. The prime 65521
  lowers the rank of every piece of $(x^5,y^7,(x+y)^{12})$, whose
  codimension is 28899. It does the same for the existing unlucky-prime
  tests, such as $(x^2,y^3,(65521x+y)^5)$. The retry is lazy: inputs proved
  modulo 65521 never pay for it.
* *Powers of $h$.* The powers modulo each prime are computed by modular
  multiplication. Integer powers are formed only for exact ranks.

**Why it is generic.** The method and its certificate are unchanged. The
change only reorders which ranks are computed exactly, and replaces a
constant cap with bounds that come from the input and from memory. Nothing
depends on particular exponents.

**Behavior change (approved).** Inputs that previously ran past weight 160
are now answered by `graded_tangent_ranks` with a `last_weight` instead of by
`graded_graph`. The finiteness and value are unchanged; see the checks below.
The user approved this change on this branch.

  unlucky-prime inputs of `test_mixed_forms_with_bad_modular_rank` are
  among the identical records: same method, value and last weight.

  ran with a 10 s limit. It agreed on every triple it finished, 26 of the
  60. These include (4,5,9), (3,7,10), (3,5,13), (2,7,13), (2,9,11), (3,5,14)

* *Independent reference.* A scratch C++ port of the construction in
  `tests/test_ae_coprime_reference.py` was used. It builds the unreduced
  matrices without the pivot division, the Euler identity or the
  Cayley–Hamilton bound, and takes ranks modulo two 62-bit primes. It
  agreed on both the value and the last weight for (5,6,7), (4,5,11),
  (4,7,9), (3,7,11), (5,7,8), (5,7,9), (5,7,12) and (4,9,13). The last two
  need the second prime.
* *Tests.* `tests/test_ae_graded.py` now also checks (4,5,9) = 5182 and
  (3,7,10) = 7090.

**Remaining.** A map constructed to be unlucky for both primes, such as
$(x^2,y^3,(65521\cdot 65519\,x+y)^5)$, declines. Graph elimination then
returns the correct value 115 in 0.18 s with method `graded_graph`. Maps of
infinite codimension in this family still end in graph elimination.

## 3. Jet rows (`native/ae_codimension.cpp`, commit `e7ae909`)

**Hot spot.** `perf record -g` of the dense plane map
$(u,uv+v^7)$, with $u=x+y+xy+y^2$ and $v=y+y^2$, 50 solves:

```
 8.12%  __gmpz_mul
 6.04%  atlas::local::ae_codimension
 5.95%  cfree
 4.75%  __gmpq_mul
 4.03%  malloc
 4.02%  (anonymous namespace)::accumulate(std::map<unsigned, mpq_class>&, ...)
 3.96%  __gmpz_gcd
 3.77%  __gmpn_gcd_1
 3.21%  std::_Rb_tree_increment
 2.93%  __gmpz_realloc
 2.28%  std::_Rb_tree_insert_and_rebalance
```

The jet certificate stored rows as `std::map<Index, mpq_class>`. Every
update allocated a tree node and canonicalized a GMP rational with a gcd.

**Change.** Rows are now column-sorted vectors of FLINT `fmpq`, which keeps
small numerators and denominators in the words themselves. A reduction is
a merge with the pivot row. Products are collected and combined once.

**Why it is generic.** This is the jet certificate for any map without a
shortcut, and it runs for every map before graded methods are tried. The
arithmetic stays exact, so pivots, counts and the work budget are charged
at the same points.

**Timings.** Benchmark maps from `benchmarks/ae_codimension.py`, fresh
process, 5 runs. "Before" is the build with changes 1 and 2:

| --- | ---: | ---: | ---: | ---: |
| Dense plane map after a coordinate change | 15.6 ms | 8.3 ms | 9.20 ms | 1.69 ms |
| Plane map after a coordinate change | 7.0 ms | 6.7 ms | 0.46 ms | 0.23 ms |
| Sharland $\widehat B_3$ | 8.0 ms | 7.4 ms | 1.71 ms | 1.22 ms |

**Verification.** All 179 comparable records of the 220 inputs were

three changes. The AE test modules (41 tests) pass.

## Remaining slow cases and ideas not implemented

* **Infinite codimension in the surface family.** The rank method cannot
  prove infinity, so graph elimination decides. That still takes minutes to
  hours for larger degrees. Ideas:
  * A native module Gröbner basis over $\mathbb Q[x^a,y^b]$, which Singular's
    module script uses.
  * A regularity bound that turns a nonzero piece past it into a proof of
    infinity.
* **Weighted tangent ranks** (`native/ae_weighted_ranks.cpp`,
  `native/ae_weighted_quotient.cpp`). Sharland's $\widehat B_7$ spends 95% of
  its 0.75 s in `WeightedQuotient::finish`. Exact nullspaces there are
  carried from one weight to the next, so the deferral in entry 2 does not
  apply directly.
* **Plane local standard bases** (`plane_jet_basis` in
  `native/local_basis.cpp`). They keep rows as `std::map<unsigned,
  mpq_class>`, the pattern removed in entry 3.
* **Graph elimination.** The modular route spends most of its time in exact
  verification: 128 of 143 s on the (2,5,7) graph ideal.
* **Process start.** The system FLINT and OpenBLAS are linked with
  `BIND_NOW`, so each native CLI process spends about 5–9 ms in the dynamic
  loader. A program that only links FLINT starts in about 6 ms, against
  0.4 ms without it. This is packaging, not Atlas code.
* **Dropped idea.** Scaling exponents by the weights would make the
  weighted-homogeneous graph ideal standard-homogeneous. It gave the same
  heads but was 8× slower on (2,3,5).

## Reproducing

```sh
python3 benchmarks/ae_compare_builds.py record --output /tmp/ae-inputs.json
python3 benchmarks/ae_compare_builds.py compare /path/to/baseline/native/build native/build /tmp/ae-inputs.json
printf 'x,y\nx^5\ny^7\n(x+y)^9\n' | native/build/bench_ae_codimension 1 solve-once
```

The header of `benchmarks/ae_graph_basis_kernel.cpp` explains how to build
and run the graph-basis timings.
